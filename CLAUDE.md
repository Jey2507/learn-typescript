# learn-typescript — контекст для Claude

Цей проєкт (Vite + TS шаблон, порожній `main.ts`/`counter.ts` не чіпаємо) —
навчальний. Користувач вивчає TypeScript через практику: **я пояснюю теорію +
даю приклад -> він пише код -> я перевіряю через `tsc --noEmit` і фідбек**.

Спілкуємось українською.

## Формат роботи (важливо дотримуватись у нових сесіях)

1. Вправи лежать у `src/exercises/NN-тема.ts` — кожен файл: докладна теорія
   з прикладами під кожним пунктом (не скорочувати, користувач просив
   "більше пояснень", бо погано пам'ятає конспект), потім `ТВОЄ ЗАВДАННЯ`
   з пронумерованими пунктами, потім `// 1.` `// 2.` ... заготовки.
2. Користувач пише код прямо в цьому файлі під заготовками.
3. На "перевір"/"готово" — читаю файл, запускаю
   `npx tsc --noEmit` (працюючий шлях — `cd` у корінь проєкту), перевіряю:
   - чи компілюється,
   - чи типізація дійсно щось гарантує (не `any`-заглушки),
   - чи виконані ВСІ пункти завдання буквально (був випадок, коли він
     писав пояснення словами замість реального рядка коду, що мав
     викликати помилку компілятора — треба наполягати на "живому" прикладі),
   - логічні баги окремо від типових (TS не ловить логіку, тільки форму
     даних — цю тезу вже кілька разів проговорювали, він її засвоїв).
4. Якщо я сам( ) допускаю помилку в прикладах теорії (напр. невикористані
   змінні при `noUnusedLocals: true` в tsconfig) — чесно визнаю, що це
   моя помилка, не його.
5. Важливо: `tsconfig.json` має `noUnusedLocals`/`noUnusedParameters: true` —
   будь-який приклад у теорії мусить або використовувати оголошене,
   або мати `void x;` / `console.log(x)`, інакше `tsc` шумітиме на
   учительський код, а не на роботу студента.

## Прогрес (оновлювати після кожної закритої вправи)

- [x] 01-basic-types.ts — базові типи, inference vs annotation, union,
      literal types. Виконано, з логічними багами що виправлені
      (межі порівнянь, переплутані напрямки) — тему засвоєно.
- [x] 02-objects.ts — типізація об'єктів, `type` vs `interface`,
      optional (`?`), `readonly`, вкладені об'єкти, масиви об'єктів.
      Виконано; засвоєно різницю "форма даних" vs "бізнес-логіка".
- [x] 03-discriminated-unions.ts — discriminated unions, narrowing через
      `switch`, exhaustiveness check (`const x: never = ...`). Виконано,
      реально відтворив і побачив помилку TS2322 при додаванні нового
      варіанту без обробки — розуміє суть патерну.
- [x] 04-generics.ts — generics (`<T>`), generic constraints
      (`K extends keyof T`), typed `map`/`filter`/`find`, type predicates
      (`arg is X`) для звуження union у масивах. Виконано. Ця тема далась
      важче за попередні — довелось кілька разів переформулювати пояснення
      (аналогія "дірка для типу", потім розбір `<T>` після імені функції
      як оголошення scope), і зрештою показати повний код для find/undefined
      напряму, бо студент застряг на "з чого почати". Після цього звірив
      розуміння через 2 контрольні питання (чому `Car | undefined`, що
      робить narrowing в `if`) — відповів правильно на обидва, тема засвоєна,
      просто потребувала більше повторів/прикладів ніж 01-03.
- [ ] 05-utility-types.ts — `Partial`, `Pick`, `Omit`, `Record`,
      `ReturnType` тощо.
- [ ] 06-classes.ts — класи, `implements`, модифікатори доступу
      (`private`/`protected`/`public`), abstract class.
- [ ] 07-unknown-and-external-data.ts — `unknown` vs `any`, narrowing
      зовнішніх/API-даних (типізація JSON-відповідей).
- [ ] 08-function-types.ts — типи функцій як значень
      (`type Fn = (x: number) => void`), overloads.
- [ ] 09-async.ts — `Promise<T>`, `async`/`await`, типізація помилок.
- [ ] 10-mini-project.ts (опційно) — маленький типізований in-memory
      "API" з CRUD, що зв'язує всі теми разом.
- [ ] (опційно, бонус) mapped types, conditional types,
      template literal types — просунутий рівень, не обов'язковий.

## Рівень користувача (станом на вправу 4)

Junior/beginner-intermediate: впевнено читає помилки компілятора, розуміє
різницю "типізовано правильно" vs "логічно правильно", сам іноді
розширює завдання (наприклад, тестує обидва випадки функції). Потребує
докладних пояснень з прикладами (погано пам'ятає теорію з конспекту,
явно просив "давай більше пояснень") — не скорочувати теоретичну частину
файлів вправ.

Важливо (виявлено на generics): коли тема абстрактніша за object/union
(тобто коли треба тримати в голові кілька рівнів непрямості — "тип
залежить від типу"), одного текстового пояснення й одного проходу
завдання МОЖЕ БУТИ НЕДОСТАТНЬО. Робочий porядок ескалації, який спрацював:
1) аналогія (generic = "дірка для типу", як параметр функції, але для типів);
2) розбір конкретного синтаксису, який плутає (`<T>` після імені функції —
   це оголошення scope, а не магія);
3) прив'язати нове завдання до вже наявного working-прикладу в тому ж
   файлі ("зроби те саме, що вище, з іншими назвами") — це спрацювало
   для завдань 2-3;
4) якщо і це не допомагає (сказав "все одно важко, не знаю з чого
   почати") — просто показати повний код з поясненням рядок-за-рядком,
   а потім перевірити розуміння контрольними питаннями (2-3 прості
   питання без коду). Не соромитись одразу переходити до варіанту 4,
   якщо студент явно каже, що пояснення не допомагають — не наполягати
   на "спробуй ще раз сам" повторно, це лише фрустрував.
